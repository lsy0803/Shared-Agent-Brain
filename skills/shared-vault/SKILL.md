# Shared Vault

Help trusted agents build on the user's knowledge without a central writing bottleneck.

## Establish the target

Use the vault path the user provides or an unambiguous existing project pointer. If several plausible vaults exist, clarify the target before writing. Read applicable host rules and the vault's collaboration protocol on first use or when changed. Respect existing paths and user preferences; do not impose the starter layout on an established vault.

This Skill is instructions, not a file interface, automatic memory service or permission grant. A repository containing a public starter is not itself a private memory store. If the task concerns this public package, edit the package only; do not fill its sample profile with real user information.

## Retrieve only what the task needs

- For a project handoff, read its current state, next action and relevant artifacts.
- Retrieve profile entries when personal context affects the decision.
- Search project history or reusable lessons when choosing an approach, recalling previous work or investigating a related failure.
- Use indexes to find material, then read the original passages needed for the decision.
- Reuse stable context already read in the current session. Re-read after context loss, an update notice, conflicting evidence or a changed target. Do not claim durable caching.

Ordinary questions and self-contained small edits do not require reading the full profile or all lessons.

## Maintain directly

An authorized agent may create and maintain task-relevant notes without routing every edit through a particular vendor or central agent. Follow narrower user or project authorizations when present.

Before editing an existing note, read its current relevant content and check for intervening changes. Preserve valid and unrelated contributions. If another writer is active or the baseline changed, reconcile the current version or use a separate draft instead of overwriting.

Keep an important update attributable with the agent, date, source and scope. One short update line is enough for a small change; there is no mandatory proposal form for routine maintenance.

## Correct with evidence

A user correction, primary source or reproducible result may justify revising another agent's conclusion. Check the old and new evidence, apply the smallest correction, and briefly explain what changed and why. Keep the current conclusion clear; preserve existing supersession links when present.

An inference is not a user fact or verified result. If evidence still conflicts, keep the uncertainty visible and use the vault's dispute process. Request independent review or the user's decision only when it resolves a material uncertainty.

## Record selectively and hand off

Save durable requirements, decisions, meaningful results, current state and useful next steps in their existing authoritative notes. Avoid duplicating updates across multiple ledgers or appending a diary after every conversation.

Apply the user's sensitive-data and consent rules. Do not store credentials or copy raw private transcripts into general memory. Maintenance authorization does not authorize public publication.

Check the changed content and links. Report what was saved, what remains unconfirmed and what was omitted. Distinguish files written from another agent having read them, and local commits from remote synchronization.
